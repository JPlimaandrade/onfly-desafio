2. Entendendo a Sintaxe de Funções no Python
Para quem vem do Java, a sintaxe de funções no Python é bem simples, mas tem alguns pontos importantes:

def convert_to_brl(amount: Decimal, currency: str, rates: dict[str, Decimal]) -> Decimal:

def: É a palavra reservada para declarar uma função (equivalente ao public void ou public Retorno no Java).

convert_to_brl: Nome da função em formato snake_case (padrão de convenção do Python, enquanto Java usa camelCase).

Type Hints (amount: Decimal, currency: str, etc.):

No Python, a tipagem é dinâmica, mas a partir do Python 3.5 podemos usar type hints para documentar os tipos esperados.

currency: str indica que currency deve ser uma String.

rates: dict[str, Decimal] indica que rates é um Dicionário (equivalente a um Map<String, BigDecimal> no Java), onde a chave é uma String (código da moeda,

-> Decimal: Indica o tipo de retorno da função (equivalente ao tipo que vem antes do nome do método no Java).

É nessa formatação para string que o .quantize() deve entrar!

2. O que é rounding=ROUND_HALF_UP?
No Java, é o equivalente ao famoso RoundingMode.HALF_UP do BigDecimal.



É a regra clássica de arredondamento escolar ("metade para cima"):

Se o dígito seguinte for 5 ou maior, arredonda para cima.

Se for menor que 5, arredonda para baixo (trunca).

Exemplo prático em Python:

from decimal import Decimal, ROUND_HALF_UP

# Exemplo 1: 10.125 -> o próximo dígito é 5, sobe para 10.13
val1 = Decimal("10.125").quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)
print(val1) # Exibe: 10.13

# Exemplo 2: 10.124 -> o próximo dígito é 4, mantém 10.12
val2 = Decimal("10.124").quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)
print(val2) # Exibe: 10.12

Se você não especificar rounding=ROUND_HALF_UP, o Python usa por padrão ROUND_HALF_EVEN (arredondamento bancário), que às vezes arredonda o .5 para o número par mais
próximo. Por isso o README pede explicitamente o half-up.

O Bug do Bloco try/except

Quando o Python executa date.fromisoformat("data-invalida") ou int("abc") ou Decimal("xyz"), é nessas linhas que ValueError e InvalidOperation são lançados —
não dentro do construtor Reservation(...)! Como elas ficaram acima do try:, o except nunca vai capturar esses erros, e o programa vai quebrar com erro não tratado (exit code
1) em vez de InputFileError (exit code 2).

Como Corrigir e Melhorar
Coloque todas as conversões e validações dentro do try::

def parse(self, raw: RawRow) -> Reservation:
    values = raw.values
    try:
        checkin = date.fromisoformat((values.get("checkin_date") or "").strip())
        checkout = date.fromisoformat((values.get("checkout_date") or "").strip())
        if checkout < checkin:
            raise ValueError("checkout antes do checkin")

        rooms = int((values.get("rooms") or "").strip())
        if rooms <= 0:
            raise ValueError("rooms deve ser maior que zero")

        amount = Decimal((values.get("amount") or "").strip())
        status = (values.get("status") or "").strip().upper()
        currency = (values.get("currency") or "").strip().upper()

        return Reservation(
            reservation_id=(values.get("reservation_id") or "").strip(),
            traveler_name=(values.get("traveler_name") or "").strip(),
            company_id=(values.get("company_id") or "").strip(),
            hotel_id=(values.get("hotel_id") or "").strip(),
            hotel_name=(values.get("hotel_name") or "").strip(),
            city=(values.get("city") or "").strip(),
            country=(values.get("country") or "").strip(),
            checkin=checkin,
            checkout=checkout,
            rooms=rooms,
            status=status,
            currency=currency,
            amount=amount,
            payment_method=(values.get("payment_method") or "").strip(),
            line_number=raw.line_number,
        )
    except (ValueError, InvalidOperation) as err:
        raise InputFileError(f"linha {raw.line_number} inválida: {err}") from err
